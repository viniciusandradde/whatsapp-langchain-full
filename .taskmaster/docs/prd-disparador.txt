# Overview

O Disparador Nexus incorpora ao ChatNexus um clone funcional do produto comercial "Disparador" (extensao Chrome de captura+disparo em massa pelo WhatsApp), integrado ao modulo Campanhas existente. A funcao PRINCIPAL e capturar os contatos, grupos e MEMBROS de grupos do WhatsApp do usuario, trazendo-os para o Nexus, e permitir disparo em massa segmentado por esses dados.

Quem usa: empresas multi-tenant do ChatNexus (operadores de marketing/vendas) que hoje disparam manualmente ou via produtos externos nao-oficiais. Valor: trazer captura + disparo para dentro da plataforma ja governada (RLS por empresa, planos, auditoria), com salvaguardas anti-ban que os produtos externos tem (jitter, validacao de numero) e que o nosso dispatcher atual NAO tem.

Fonte canonica do produto: a pasta docs/Baileys/ contem o codigo real do ecossistema que inspirou o produto - o projeto open-source whatsapp-api-nodejs (REST sobre Baileys 4), o frontend de disparo em massa (ZDGText.js/ZDGFile.js), screenshots da extensao comercial "Disparador PRO" e planilhas que provam o produto-promessa (extrair telefones de membros de grupo -> disparar). NOTA: o plano original assumiu por engano que essa pasta nao existia; este PRD corrige isso e incorpora os achados.

# Core Features

1. Auth da extensao por API key por empresa - token nxs_<empresa_id>_<32hex>, armazenado como key_hash sha256 (nunca o segredo), com scopes (capture/dispatch/templates), expires_at opcional, rotacao e revoked_at. Superior ao ?key= em querystring dos tutoriais (anti-padrao que vaza em logs). Resolve a empresa pela key e ativa o contexto RLS.

2. Captura para STAGING (nao direto no CRM) - contatos raspados sao sujos (push-name, sem consentimento/LGPD). Caem em contato_capturado (staging) com wa_jid como identidade primaria (telefone derivado/opcional, pois membros multi-device aparecem como @lid sem telefone). O usuario promove os escolhidos para cliente. Grupos e membros tem tabelas proprias.

3. Dois caminhos de captura - (a) extensao Chrome via hook do window.Store do WhatsApp Web; (b) server-side via Evolution API (/chat/findContacts, /group/fetchAllGroups?getParticipants=true). Membros de grupo exigem fetch separado (groupMetadata por grupo), pesado/rate-limited -> captura assincrona com captura_lote.status.

4. Disparo em massa anti-ban - reusa o dispatcher duravel existente (_dispatch_loop, status por destinatario, abort, contadores) mas adiciona o que o produto-fonte tem e nos nao: JITTER aleatorio (intervalo min/max por destinatario, nao fixo), validacao onWhatsApp antes do envio, presenca composing, variaveis por destinatario (placeholders [field1..N] do CSV), e estagio Preparar->ENVIAR (preview com contagem + invalidos).

5. Compliance estrutural - lista de opt-out/supressao (captura STOP no worker), caps diferenciados por provider (Evolution baixo vs WABA por tier), quiet hours, warmup de numero novo, kill-switch automatico, e aviso ToS bloqueante. Volume e empurrado para WABA (rota oficial sustentavel).

6. API Oficial (WABA) - aba que reusa o fluxo de Embedded Signup e os templates HSM ja entregues; origem janela 24h (DISTINCT de message_queue).

7. Gating por plano - Free (25 contatos, so texto) vs Premium (ilimitado, midia, templates). Cap via features[disparador_max_contatos].

# User Experience

Personas: operador de marketing (cria campanhas, captura listas), admin da empresa (gera/revoga API keys), destinatario final (opt-out).

Fluxos-chave:
- Conectar: reusa o modal de QR existente (connections/evolution-qr-modal.tsx, polling) - nao reimplementar Socket.IO.
- Capturar: extensao injetada no WhatsApp Web (aguarda o Store hidratar) OU botao Capturar via Evolution no painel -> contatos/grupos/membros caem no staging -> browser em /disparador/contatos/ com Promover p/ CRM e total disponivel mesmo truncado (upsell 100 de 1210).
- Disparar: create de campanha com selector de origem (manual|grupos|contatos|janela 24h|segmento), campos de intervalo min/max, Preparar (valida/conta, mostra invalidos) -> ENVIAR (so habilita apos Preparar) -> progresso por destinatario via polling.
- Extensao: layout vertical unico, abas de canal data-driven por Conexao.provider, campos NUMEROS/Validar/Contatos/Grupos/Modelo/Anexar/Intervalo. Bearer header, nunca ?key=.

# Technical Architecture

## Componentes
- API FastAPI (server/): novos routers captura.py (sob verify_api_key), captura_evolution.py e disparador.py (sob service-token + get_empresa_context); CRUD api-keys. Reusa waba_templates.py.
- Worker (worker/): evolution_client.py ganha fetch_contacts, fetch_groups, fetch_group_participants, check_numbers, send_media_url, send_reaction, health. Captura de STOP no process_message. NOTA: hoje evolution_client.py so tem send_message+send_typing.
- Shared: api_key.py (resolucao/hash sob bypass), captura.py (normalizador unico de shape store: telefone so de @s.whatsapp.net, is_business=verifiedName!=null, getWhatsAppId; upserts idempotentes; promocao). campanha.py ganha resolver no create, jitter no loop, variaveis por destinatario, opt-out, quiet hours, kill-switch. plano_limits.py ganha caps por provider.
- Extensao Chrome MV3 (extension/, dir top-level novo, em quarentena): background SW + content (scrape.ts/store-hook.ts via moduleRaid->window.Store) + popup + options + lib/api.ts (Bearer). Versionada a parte, fora do make ci, zip standalone (NAO proxiada por /uploads).
- Frontend (frontend/src/app/disparador/): api-keys/, contatos/, e extensao do create de campanhas/. Espelha o padrao actions.ts->@/lib/api->service token.

- 121 - permissoes + features + compliance: permissao rows disparador.{capturar,disparar,api_key.manage,template.manage}; plano.features keys disparador (bool), disparador_media (bool), disparador_max_contatos (int Free=25); disparador_opt_out (empresa_id, telefone, origem, created_at; UNIQUE (empresa_id,telefone)) + RLS; campanha += janela_inicio, janela_fim, kill_switch_pct.

## APIs
- Auth: verify_api_key -> ApiKeyContext(empresa_id, key_id, scopes) - HTTPBearer(auto_error=False); 401 ausente/invalida, 403 require_scope, NUNCA 500; hmac.compare_digest sobre o HASH (nao o segredo); lookup por key_prefix indexado sob empresa_scope(None, bypass=True); chama set_request_context(empresa_id). shared/api_key.py::resolve_api_key. Molde: verify_service_token (dependencies.py:113-155).
- Captura extensao (Depends(verify_api_key)): POST /api/captura/{contatos|grupos}, POST /api/captura/grupos/{wa_group_id}/membros (batch cap ~2000/req, upsert idempotente, grava captura_lote). Pydantic discrimina contato (@s.whatsapp.net) vs grupo (regex 18 digitos @g.us) com 422 por campo. Persiste JID/telefone CRU; normaliza so na promocao.
- Captura Evolution (service-token + get_empresa_context): POST /api/conexoes/{id}/captura/{contatos|grupos}; membros como background task (asyncio.create_task+_BG_TASKS, captura_lote.status). GET leitura retorna total_disponivel mesmo truncado pelo gating. GET /api/disparador/contatos-unicos?grupo_ids= (DISTINCT wa_jid cross-grupo = LEADS UNICOS).
- Disparo: POST /api/disparador/preview (resolve origem -> count_valido, count_invalido, sample, total_disponivel); create chama create_campanha existente; gating count Free<=25 -> 402. GET /api/disparador/janela-24h?conexao_id=.
- EvolutionClient novos: fetch_contacts (POST /chat/findContacts/{instance}), fetch_groups (GET /group/fetchAllGroups/{instance}?getParticipants=true), fetch_group_participants, check_numbers (POST /chat/whatsappNumbers/{instance}), send_media_url, send_reaction (POST /message/sendReaction/{instance}), health (/instance/info). Padrao: httpx + header apikey + normalize_to_number (ja existente).

## Dispatcher (mudanca minima, duravel ja existente)
- _dispatch_loop mantem batches de 50, status por destinatario, abort, contadores, _BG_TASKS. Muda: troca asyncio.sleep(intervalo_s) FIXO (linha 473-474) por random.uniform(intervalo_min_ms, intervalo_max_ms)/1000 por destinatario (fallback intervalo_ms quando min==max); respeita quiet hours; auto-abort se falhas/enviados > kill_switch_pct. _resolve_template_vars (linha 304) estendido para mesclar variaveis do destinatario sobre template_variaveis (placeholders [field1..N]/{{var}}, {{nome}} retrocompat). Resolver de origem + validacao check_numbers + filtro opt-out rodam no create (nao no loop).

## Infra/seguranca
- Cada tabela nova self-enrola RLS na propria migration (mig 101 nao pega novas). set_request_context obrigatorio no caminho API-key. Extensao em quarentena (so /api/captura/* scope capture, sem service token). Midia preferencialmente por URL (evita gotcha rewrite /uploads).

# Logical Dependency Chain
1. S0 (API keys + RLS) primeiro - fundacao de auth e ponto unico de falha (isolamento de tenant). Nada de captura sem isso.
2. S1 (captura Evolution) depende de S0 - prova o cano de dados (staging+dedup+membros+promocao) em CI com mock, ANTES do scraper fragil. Funcao principal, entregavel e visivel (browser de contatos no painel).
3. S2 (targeting) depende de S1 - conecta os dados capturados ao disparo; entrega a primeira campanha real ponta-a-ponta (origem=grupos -> preview -> envio com jitter).
4. S3 (compliance) depende de S2 - endurece o disparo ja funcional.
5. S4 (API Oficial) depende de S2 - reusa o resolver/gating; pode ser paralelo a S3.
6. S5 (extensao) depende de S0+S1 - o backend de captura tem que existir e estar validado antes do scraper.
7. S6 (ricas) depende de S4 - botoes precisam do caminho WABA.

Cada slice e um vertical entregavel (BE+UI+E2E) que pode ir a producao isolado, respeitando foco em 1 modulo por vez.

# Risks and Mitigations
- ToS/ban (P0): jitter aleatorio, validacao onWhatsApp, opt-out, quiet hours, kill-switch, warmup, caps por provider, aviso bloqueante, empurrar volume p/ WABA.
- RLS no caminho API-key (P0): set_request_context em verify_api_key; RLS self-enroll por migration; TestE2EIsolamento primeiro (ambas direcoes).
- Identidade por telefone perde membros so-LID (P0): wa_jid como chave, telefone NULLABLE; espelha cliente.whatsapp_lid (mig 046).
- Dispatcher in-process (P1): path reenviar pendentes; fix duravel (worker via message_queue) = divida fora de escopo.
- Rate limit/latencia Evolution (P1): captura assincrona (captura_lote.status), paginacao, cap, membros como lote dedicado, re-captura idempotente.
- Extensao fragil (P1): hook Store > DOM, seletores isolados + scrape-health + versao, quarentena, ADR nao-hospedar-nodeback.
- plano.limite_* NULL=ilimitado (P2): cap Free via features, nao colunas limite.
- Gotcha /uploads (P2): midia por URL preferencial; upload local secundario com ARG no build.
- Mensagens ricas que nao renderizam (P2): gatear por provider (botao so WABA); so send_reaction em conta pessoal; pagamento!=PIX.
